# Railway official docs: capabilities for live verification, testing and safe experiments

Researched 2026-09-30 through the Railway MCP `search-docs` and `fetch-docs` tools. Direct HTTP access to docs.railway.com was blocked by the egress proxy, so WebFetch and curl were not used.
- **[F]** means the full page was fetched and read. Quotes marked [F] are exact.
- **[S]** means a `search-docs` index excerpt only. This applies to `/guides/*` pages, which `fetch-docs` returned as "No page exists" even though search indexes them. Quotes marked [S] are exact excerpt text.
- Nothing was changed on Railway. No variable values were read.

Target stack: about 20 services, a custom PostGIS image, Redis, NATS JetStream, FastAPI, an nginx gateway, and a one-shot migrator.

## 1. Environments

| Capability | Exact caveat / limit | URL | Use for us |
|---|---|---|---|
| **Persistent environments** (e.g. `staging`) | "All changes made to a service are scoped to a single environment." Each environment has its own isolated private network. | https://docs.railway.com/environments [F] | Keep a long-lived `staging` that auto-deploys from a `staging` branch, as a full replica for experiments. |
| **Duplicate Environment** (UI) / `railway environment new X --duplicate production` (alias `--copy`) | Copies "services, variables, and configuration". Services are then "staged for deployment" and "You must review and approve the staged changes before the services deploy". **Sealed variables are NOT copied.** Volume **contents**: the docs only say "a duplicated environment gets its own database services with their own volumes and data" [S, /guides/isolate-staging-production]. Copying production data is **not documented**. | https://docs.railway.com/environments [F] · https://docs.railway.com/cli/environment [F] · https://docs.railway.com/variables#sealed-variables [F] | Create a throwaway env for an experiment. You must seed it yourself; Railway does not clone the data. |
| **API env create options** | `environmentCreate` takes `sourceEnvironmentId` ("Clone variables and settings"), `ephemeral`, `skipInitialDeploys` ("Don't trigger deployments on creation") and `stageInitialChanges`. `environments(isEphemeral:false)` filters out PR envs. | https://docs.railway.com/integrations/api/manage-environments [F] | Script "clone prod config, deploy nothing yet". You can then inspect and deploy only the 3-4 services an experiment needs. |
| **Sync environments** | Imports services from another env as staged changes tagged "New / Edited / Removed". Sealed variables are "not shown as part of the diff when syncing". | https://docs.railway.com/environments#sync-environments [F] | Promote a verified staging config into prod as a reviewable diff. |
| **PR environments** | Created on PR open and "deleted as soon as these PRs are merged or closed". They will not deploy PRs from users outside the workspace. Auto-domains only when the base env services use Railway-provided domains. The base env is prod by default and can be changed ("you can change which environment PR Environments inherit from" [S]). | https://docs.railway.com/environments#pr-environments [F] | Per-PR live smoke tests. Point the base at `staging`, not prod. |
| **Focused PR environments** (Priority Boarding) | Deploys only services affected by changed files (watch paths or root dir) plus their reference-variable dependencies. Other services are skipped and can be deployed manually. | same [F] | Cuts a 20-service PR env down to the touched subgraph. |
| **Bot PR environments** | A toggle that creates environments for PRs from Dependabot, Renovate, Claude Code, etc. | same [F] | Live-verify dependency bumps, e.g. pip-audit-driven upgrades. |
| **Config overrides per env / PR** | Config-as-code `environments.<name>` and the special `pr` block. Priority order: named ephemeral env, then `pr`, then the PR's base env, then base config, then service settings. | https://docs.railway.com/config-as-code/reference [F] | Give PR envs a different start command, e.g. seed plus smoke. **Deprecated, see §6.** |
| **Canary-honesty warning** | "By default the canary copies production's variables, which may include a production `DATABASE_URL`." [S] | https://docs.railway.com/guides/ship-on-merge-pr-canaries#keep-canaries-honest [S] | Critical: a PR or duplicate env can write to prod data if a variable is a literal URL instead of a `${{Postgres.DATABASE_URL}}` reference. |
| **Cost** | "If you have 5 open PRs, you may be running 5x your normal workload." | https://docs.railway.com/pricing/understanding-your-bill [F] | Use Focused PR envs and close PRs promptly. |
| **Environment RBAC** (Enterprise) | Non-admins can't access prod variables, logs or metrics, but "can still trigger deployments via git push". | https://docs.railway.com/environments#environment-rbac [F] | Not applicable unless on Enterprise. |

## 2. Deployments

| Capability | Exact caveat / limit | URL | Use for us |
|---|---|---|---|
| **Healthcheck (deploy-time gate only)** | Railway polls the path until any `2xx`, then switches traffic. "Railway does not monitor the healthcheck endpoint after the deployment has gone live." Default timeout 300s; override with `RAILWAY_HEALTHCHECK_TIMEOUT_SEC`. The request comes from host `healthcheck.railway.app`; an app that restricts Host gets "failed with status 400". It uses the `PORT` variable, so set `PORT` if you use target ports. It is HTTP only: "That check is HTTP only" [S, alerts guide]. | https://docs.railway.com/deployments/healthchecks [F] | Make `/readyz` the gate on every FastAPI service. **Allow `healthcheck.railway.app` in FastAPI TrustedHost and the nginx `server_name`.** No continuous monitoring, so bring your own prober. |
| **Volume services cannot overlap** | "we prevent multiple deployments from being active and mounted to the same service ... small amount of downtime ... even if there is a healthcheck". | same [F] | Postgres, Redis and NATS (with volumes) always blip on redeploy. Never redeploy them as part of an experiment. |
| **Deployment states** | Initializing, Building, Deploying (waits on the healthcheck), Active, Completed (exit 0), Crashed, Failed, Removed. The API lists `BUILDING, DEPLOYING, SUCCESS, FAILED, CRASHED, REMOVED, SLEEPING, SKIPPED, WAITING` ("waiting for approval"), `QUEUED`. **`NEEDS_APPROVAL` appears nowhere in the docs.** The documented approval status is `WAITING`, which Wait-for-CI also uses. | https://docs.railway.com/deployments/reference [F] · https://docs.railway.com/integrations/api/manage-deployments [F] | Poll status via API or CLI as the verification gate. The migrator should end in `Completed` (`SUCCESS` in the API). |
| **Overlap / draining** | `RAILWAY_DEPLOYMENT_OVERLAP_SECONDS` (default 0). `RAILWAY_DEPLOYMENT_DRAINING_SECONDS`, the SIGTERM-to-SIGKILL gap, "default ... 0". | https://docs.railway.com/deployments/deployment-teardown [F] · https://docs.railway.com/variables/reference [F] | Set draining to about 15-30s on FastAPI and NATS consumers. The default of 0 kills in-flight requests and messages. |
| **Rollback** | Restores "Both the Docker image and custom variables". Only works within image retention: Free/Trial 24h, Hobby 72h, Pro 120h, Enterprise 360h. Outside that window only redeploy is available, which rebuilds from source. It does **not** touch volume data (no statement about data; rollback is image plus variables only). | https://docs.railway.com/deployments/deployment-actions [F] · https://docs.railway.com/pricing/plans#image-retention-policy [F] | A fast undo for a bad experiment. Irreversible migrations still need a backup or PITR first. |
| **Redeploy / Restart / Abort / Remove** | Redeploy uses "the exact same code and build/deploy configuration". Restart restarts the process without a rebuild. Abort cancels Initializing or Building. | same [F] | Restart is for reproducing startup-order bugs without a rebuild. |
| **Deploy ordering by reference vars** | Applies to template deploys, staged-change applies, env duplication and PR envs. It does **not** apply to "GitHub push deploys — even in a monorepo" or single-service redeploys. Cycles deploy in parallel. | https://docs.railway.com/deployments/deployment-actions#deployment-dependencies---startup-ordering [F] | Monorepo pushes give no ordering guarantee, so services must tolerate Postgres or NATS not being ready. |
| **Pre-deploy command** | Runs between build and deploy, "within your private network" with app variables, in a **separate container**: "volumes are not mounted". A failure means "it will not be retried and the deployment will not proceed". No time limit by default. The Pre-deploy Timeout is 1-3600s and the field "only appears once you have entered a pre-deploy command". | https://docs.railway.com/deployments/pre-deploy-command [F] | An alternative to the one-shot migrator service: the migration gates the API deploy atomically. Set a timeout. |
| **Deployment approval** | A push from a GitHub user without a linked Railway account creates a "Deployment Approval" (Approve/Reject). It is skipped for Deployer role or higher with GitHub connected. | https://docs.railway.com/services#approving-a-deployment [F] · https://docs.railway.com/projects/workspaces [S] | Not a general "manual gate" feature. For gating, use Wait for CI, staged changes, or disabled autodeploy. |
| **Wait for CI** | Deployment sits in `WAITING` until all GitHub Actions check suites finish. A failure skips the deploy. Skipped or neutral runs never block. Cancelled runs block only if no other workflow passed. It skips after **2 hours**. Checks from other GitHub apps are ignored. | https://docs.railway.com/deployments/github-autodeploys#wait-for-ci [F] | Makes our CI gates (preflight, pytest -m unit, pip-audit) block Railway deploys. |
| **Staged changes** | Changes collect in a changeset with a diff. Alt+Deploy commits without redeploying. "Networking changes are not yet staged and are applied immediately". | https://docs.railway.com/deployments/staged-changes [F] | Review the diff before applying. Domain and TCP-proxy edits are live instantly. |
| **Restart policy** | Default `On Failure`, max 10. Options `Always`, `On Failure`, `Never`. Paid plans get unlimited retries. After the limit, status becomes `Crashed` and webhooks and emails fire. | https://docs.railway.com/deployments/restart-policy [F] | The migrator needs `Never`, or `On Failure` with a low count, so a failing migration does not loop. |
| **Cron services** | UTC. Runs must be at least 5 minutes apart. "if a previous execution is still running ... Railway will skip the new cron job". Timing can vary "by a few minutes". | https://docs.railway.com/cron-jobs [F] | A scheduled synthetic-check job (e.g. every 5-15 minutes) that exits. |
| **Railway-initiated redeploys** | Host migrations and patches are "mandatory and cannot be opted out of". | https://docs.railway.com/deployments/reference [F] | Expect unplanned restarts. Volume services will blip. |
| **Ephemeral disk** | 100GB on paid plans. Exceeding it means the service "can be forcefully stopped and redeployed". | same [F] | |

## 3. Observability

| Capability | Exact caveat / limit | URL | Use for us |
|---|---|---|---|
| **Logs: build, deploy, environment (Log Explorer), HTTP, DNS, network-flow** | Filter syntax: text, `"phrase"`, `@attr:value`, `AND`/`OR`/`-`, numeric `> >= < <= ..`. HTTP attributes include `@path @httpStatus @totalDuration @responseTime @upstreamRqDuration @txBytes @rxBytes @srcIp @edgeRegion @requestId`. Environment logs support `@service:<id>`. **DNS logs** support `@zone:internal` and `@rcode:NXDOMAIN`. | https://docs.railway.com/observability/logs [F] | One query across 20 services: `@level:error`. `@zone:internal AND @status:failed` catches broken `*.railway.internal` names. |
| **`railway logs`** | Streams by default. `--lines/--since/--until` switch to fetch mode. `--build`, `--http` (`--status ">=400"`, `--path`, `--method`, `--request-id`), `--network` (flows: `--peer postgres --port 5432`, `--status dropped`, `--drop-cause`), `--dns`, `--json` (NDJSON). | https://docs.railway.com/cli/logs [F] | Scriptable post-deploy assertions, e.g. zero 5xx in the last 10 minutes. Network flows show whether api → postgres or api → nats connections are dropped. |
| **Structured logs** | A single-line JSON with `message`, `level` and custom attributes becomes queryable via `@attr`. stderr maps to `error`. | same [F] | Emit `request_id` and `trace_id` as attributes. |
| **Log retention / rate limit** | Free 3d, Hobby 7d, Pro 30d, Enterprise up to 90d. **500 lines/s per replica**; excess lines are dropped. "Railway does not have a log drain setting". | same [F] | Verbose debug logging during an experiment can silently drop lines. |
| **Metrics (dashboard)** | CPU, Memory, Disk, Network, up to 30 days, with deploy markers. The metrics page says "Application-level metrics such as request latency, error rates ... are not collected by Railway". Public-network traffic shows only in the Sum view. | https://docs.railway.com/observability/metrics [F] | Before/after resource comparison across a deploy. |
| **`railway metrics --http`** | The CLI **does** give "HTTP request totals, status-code buckets, error rate, and latency percentiles", filterable by `--method` and `--path`, with `--since/--until`, `--json`, `--watch`. For DB images it adds native Postgres and Redis stats "through Railway SSH". | https://docs.railway.com/cli/metrics [F] | **The main canary signal**: compare error rate and p95 per path before and after a deploy. (This conflicts with the metrics page; the CLI page is newer and more specific.) |
| **Tracing (preview)** | Per service and per environment. The edge traces every request (no sampling) and adds `x-railway-trace-id`. A client `traceparent` header with the sampled flag forces or suppresses a trace. The OTLP receiver takes **traces only**. `OTEL_*` variables are injected on the next deploy. A setting of your own `OTEL_EXPORTER_OTLP_ENDPOINT` disables injection. Limit 1,000 spans per 10s per replica. A search returns up to 500 traces. Retention matches logs. A service without a public domain gets no edge spans. | https://docs.railway.com/observability/tracing [F] | Enable on the gateway and FastAPI. Send a forced-`traceparent` curl to follow one synthetic request across services. |
| **Python tracing** | `opentelemetry-instrument uvicorn ...`. Set `OTEL_METRICS_EXPORTER=none` and `OTEL_LOGS_EXPORTER=none`. Covers FastAPI, httpx, asyncpg, psycopg2, SQLAlchemy and redis. `OTEL_LOG_LEVEL=debug` for troubleshooting. | https://docs.railway.com/observability/tracing/python [F] | Direct fit for our FastAPI services. |
| **Auto-instrumentation (eBPF/OBI)** | No redeploy; applies "within a minute". Best effort. Python context propagation "needs the `uvloop` event loop". It does not propagate over TLS calls or across queue work. **Do not combine with an SDK** (duplicate spans). | https://docs.railway.com/observability/tracing/automatic-instrumentation [F] | Zero-code first look. NATS-driven work shows up as new traces. |
| **`railway trace`** | `status --all`, `enable [--auto-instrument]`, `list --since 30m --errors`, `list --filter '@http.route:/x @duration:>500'`, `get <id>`, `--json`. | https://docs.railway.com/observability/tracing [F] | Scriptable latency and error regression checks. |
| **Webhooks** | Per project, covering all envs. Events are deployment status changes, volume usage alerts and CPU/RAM monitor alerts. 30s timeout. Up to 3 retries. "delivery is not guaranteed and events are not ordered". **Unsigned**; add a secret custom header (up to 20 headers). Disabled for 24h after 100 failures in 6h. Payload includes `environment.isEphemeral`. Slack and Discord payloads are auto-formatted. Test button. | https://docs.railway.com/observability/webhooks [F] | Trigger a post-deploy smoke suite on `Deployment.*` events and reconcile against the API. |
| **Monitors (Pro)** | Threshold alerts on CPU, RAM, disk and egress (email, in-app, webhook). No HTTP or error-rate monitors are documented. | https://docs.railway.com/observability#monitors [F] | Disk alert on the Postgres volume. |
| **Continuous uptime** | Not built in. Docs point to the Uptime Kuma template. | https://docs.railway.com/deployments/healthchecks [F] | Run our own prober as a service or cron. |

## 4. Networking

| Capability | Exact caveat / limit | URL | Use for us |
|---|---|---|---|
| **Private DNS** `<service>.railway.internal` | WireGuard. Isolated per project and per environment. "New environments (created after October 16, 2025): ... both internal IPv4 and IPv6. Legacy environments: ... IPv6 addresses only". Use `http://` internally. | https://docs.railway.com/networking/private-networking/how-it-works [F] | Check the env creation date. In a legacy env, uvicorn, nginx and NATS must listen on `::` (docs example: `"[::]" binds IPv6 ... Required: private networking resolves to IPv6 in legacy environments` [S, ship-logs guide]). |
| **Runtime only** | "Private networking is only available at runtime, not during the build phase". Migrations "should run as part of the start command, not the build". | same [F] | Never reach Postgres or NATS from a Dockerfile `RUN`. |
| **Library notes** | ioredis and bullmq need `family=0`. Mongo needs `--ipv6 --bind_ip ::,0.0.0.0`. | https://docs.railway.com/networking/private-networking/library-configuration [F] | Python clients are not listed. Verify with DNS and network-flow logs. |
| **`railway private-network status`** | Shows endpoint status and name per service. | https://docs.railway.com/cli/private-network [F] | Read-only check of internal DNS names. |
| **Public domains / edge specs** | TLS required. HTTP/1.1 and HTTP/2. Idle HTTP/1.1 closes after 60s. Requests with no data transfer close after 5 minutes (up to 15 minutes if streaming). Websockets have no limit. Header limit 32KB. Rate limits: about 11k RPS per domain, 10k concurrent connections. Headers sent: `X-Railway-Request-Id` and `X-Request-Start`. **Clients can send `X-Railway-Debug`** to get `X-Railway-Upstream-Zone`. | https://docs.railway.com/networking/public-networking/specs-and-limits [F] | Use `X-Railway-Request-Id` to join a failing request to HTTP logs. Use `X-Railway-Debug` to verify the serving region. |
| **Auth** | Railway adds **no** application auth. Private networking gives no public exposure. Railway "do[es] not currently offer a configurable service for users' applications" as a security layer (older checklist text), but **Edge rules** now exist. | https://docs.railway.com/overview/production-readiness-checklist [F] | Anything on a public domain is open. Protect debug endpoints yourself. |
| **Edge rules** | Block, allow, challenge, redirect or cache override by client IPv4 or CIDR, host, path or header. First terminal match wins. Rules "propagate ... within a few seconds". Requires a public domain and a plan allowance. JSON editor. Limit 64 KiB. | https://docs.railway.com/networking/edge-rules [F] | Expose `/debug*` and `/experiment*` only when the request carries a secret header or comes from an office CIDR, and block everything else at the edge. |
| **TCP proxy** | Random load balancing across replicas in the closest region. Adds public exposure and egress billing. | https://docs.railway.com/networking/tcp-proxy [F] | Avoid for DB checks; use `railway connect` over SSH instead. |
| **App binding** | 502 "Application failed to respond" when the host or port is wrong. Bind `0.0.0.0` on `$PORT`: `uvicorn main:app --host 0.0.0.0 --port $PORT`. | https://docs.railway.com/networking/troubleshooting/application-failed-to-respond [F] | Note the tension with legacy IPv6-only private networking: binding `::` covers both on dual-stack (inference from the two pages). |

## 5. Volumes and data

| Capability | Exact caveat / limit | URL | Use for us |
|---|---|---|---|
| **Volume backups** | Manual or scheduled. Daily is kept 6 days, Weekly 27 days, Monthly 89 days. Manual backups are "limited to 50% of the volume's total size". A restore **mounts a new volume** named by date, keeps the old one unmounted, and is staged for review. "Wiping a volume deletes all backups". "Backups can only be restored into the same project + environment". Works for **any** volume, including a custom image. | https://docs.railway.com/volumes/backups [F] | Take a manual backup of PostGIS before every schema experiment. Restore is reviewable. You can't restore a prod backup into staging. |
| **PITR (Postgres/MySQL)** | Needs an **official image only** (`postgres-ssl` or `postgres-ha`) on a **major tag**. WAL goes via pgBackRest to a Railway bucket, giving about a 4-week window. The window starts at the first base backup after enabling. A restore **creates a sibling service** (`<source>-restored-YYYYMMDD-HHMM`) and "The source service is never touched." Billed as bucket storage plus egress. | https://docs.railway.com/volumes/point-in-time-recovery [F] | **Not available for our custom PostGIS image.** If we moved to official `postgres-ssl`, PostGIS would need to be available in it (not documented). |
| **Postgres HA** | Patroni, etcd and HAProxy. "Custom images (e.g. PostGIS, TimescaleDB) are not compatible." A pinned tag is required. | https://docs.railway.com/databases/postgresql-ha [F] | Not available for us as-is. |
| **Major version upgrade** | In place, with a read-only preflight, backups before and after, and a revert window. "Custom images are not supported." Manually editing the image tag "does not run `pg_upgrade`". | https://docs.railway.com/databases/postgresql-major-upgrade [F] | For PostGIS we have to dump and restore ourselves. Never bump the major tag directly. |
| **Postgres config** | Use `ALTER SYSTEM` plus a restart. `RAILWAY_SHM_SIZE_BYTES` defaults to 64MB. | https://docs.railway.com/databases/postgresql [F] | |
| **`railway postgres`** | `pitr status/backup create/backup list/schedule`, `ha status`, `pgbouncer status`, a local audit log. PITR and HA require the official image. `backup restore <ID>` "overwrites the selected database's data" in place. | https://docs.railway.com/cli/postgres [F] | Whether `backup create` works on a custom image is not documented; the page says PITR/HA need the official image. |
| **Live resize** | No downtime, except "when a volume reaches 100% capacity" (offline resize and restart). Pro can self-serve up to 1TB. | https://docs.railway.com/volumes [F] | Resize before 100%. Monitor disk. |
| **Volume mount timing** | Volumes are mounted at container start, not at build or pre-deploy. Mounted as root; `RAILWAY_RUN_UID=0` for non-root images. | same [F] | A custom PostGIS image running as the postgres user may need a UID fix. |
| **File inspection** | `railway volume files list/download`, `railway service files list/download` (ephemeral FS), scp/sftp over Railway SSH. | https://docs.railway.com/volumes [F] · https://docs.railway.com/services [F] | Pull a NATS JetStream store file or a Postgres log for offline analysis. |

## 6. Variables and config-as-code

| Capability | Exact caveat / limit | URL | Use for us |
|---|---|---|---|
| **Reference variables** | `${{Service.VAR}}`, `${{shared.VAR}}`, `${{VAR}}`. Also drive deploy ordering. | https://docs.railway.com/variables [F] · /variables/reference [F] | Use references (never literals) for DB and NATS URLs so duplicated or PR envs point at their own DB. |
| **Sealed variables** | Values never visible in the UI or API. Can't be unsealed. Not provided to `railway run` or `railway variables`. **Not copied** to PR envs, duplicated envs or duplicated services. | https://docs.railway.com/variables#sealed-variables [F] | A sealed secret silently missing in a PR env is a classic "works in prod, fails in preview" cause. |
| **Railway-provided variables** | `RAILWAY_GIT_COMMIT_SHA`, `RAILWAY_DEPLOYMENT_ID`, `RAILWAY_REPLICA_ID`, `RAILWAY_REPLICA_REGION`, `RAILWAY_ENVIRONMENT_NAME`, `RAILWAY_SNAPSHOT_ID`, `RAILWAY_PRIVATE_DOMAIN`. Build-time use needs `ARG` in the Dockerfile. | https://docs.railway.com/variables/reference [F] · /builds/dockerfiles [F] | Expose them on `/runtime-identity` so a probe can prove which commit and replica served the request. |
| **Config as Code (`railway.json`/`.toml`)** | **Deprecated.** "Existing Config as Code files stop being read on 2026-12-01 (hard cutoff)." New services can't opt in. Fields: builder, `watchPatterns`, `buildCommand`, `dockerfilePath`, `startCommand`, `preDeployCommand`, `multiRegionConfig`, `healthcheckPath`, `healthcheckTimeout`, `restartPolicyType/MaxRetries`, `cronSchedule`, `overlapSeconds`, `drainingSeconds`, `environments.<name>` and `pr` overrides. | https://docs.railway.com/config-as-code/reference [F] | **Action item: migrate before 2026-12-01.** |
| **Infrastructure as Code** (`.railway/railway.ts`; py/go beta) | `railway config pull/plan/apply`. **`plan` is read-only.** `plan --detailed-exit-code` exits 0 for no drift and 2 for changes pending. Values are redacted by default. `apply --plan saved.json` pins the reviewed change set. Destructive changes need `--confirm-destructive`. `ctx.environment` for per-env config. Service fields include `healthcheck`, `healthcheckTimeout`, `preDeploy`, `replicas`, `env`, `volumeMounts`, `domains`. **Tracing field "Not yet supported by the SDKs"**: an apply would turn tracing off. | https://docs.railway.com/infrastructure-as-code [F] · /infrastructure-as-code/reference [F] | `railway config plan --detailed-exit-code` in CI is a **live config-drift detector** against prod. |

## 7. CLI: which commands run inside the live private network

| Command | Runs where | Caveat | URL | Use for us |
|---|---|---|---|---|
| `railway run <cmd>` / `railway shell` | **Locally**, with the service's variables injected | Not on the private network: `*.railway.internal` will not resolve locally. Sealed variables are not provided. | https://docs.railway.com/cli/run [F] · /cli/shell [F] | Local scripts against public endpoints only. **Careful: this gives local code prod credentials.** |
| **`railway ssh [-- cmd]`** | **Inside the running container**, so it has the private network | Needs a registered SSH key. `--deployment-instance <id>` targets one replica. `--session` for tmux. SFTP/scp supported. `ssh -L` forwarding is limited to container loopback and the project private network. No VS Code Remote. Not supported with project tokens. | https://docs.railway.com/cli/ssh [F] | **Primary tool for live verification**: `railway ssh -s api -- python -m ourpkg.selfcheck` or a curl to `nats.railway.internal:8222`. Anything run here has prod blast radius. |
| **`railway connect [db]`** | Local client over a public TCP proxy **or an SSH tunnel** (auto when there is no proxy) | `--tunnel-only` prints connection details and holds the tunnel. Needs psql or redis-cli locally unless using `--tunnel-only`. | https://docs.railway.com/cli/connect [F] | Run read-only SQL checks (PostGIS version, migration table) with no public DB exposure. |
| **`railway sandbox create --private-network`** | **An isolated VM joined to the environment's private network** | Default mode is `ISOLATED` (no private network). `exec --timeout` (exit 124). Variables via `--variable DATABASE_URL=Postgres.DATABASE_URL`. Idle timeout 30 minutes by default on Hobby/Pro (1-120, 0 disables). 100 per env on Pro. Billed at **VM rates** ($50/GB-mo RAM, $50/vCPU-mo). Checkpoints and forks available. | https://docs.railway.com/sandboxes [F] · /cli/sandbox [F] · /pricing/plans#vm-pricing [F] | **Best safe experiment runner**: run integration tests or a probe **next to** the services without touching their containers, then destroy the VM. |

## Top 12 practical uses for live verification (ranked)

1. **`railway ssh -s <svc> [-e staging] -- <check>`**: run self-checks **inside** a live container with the real private network. Use `--deployment-instance` to test a specific replica. (cli/ssh [F])
2. **`railway sandbox create --private-network` plus `exec --timeout`**: an ephemeral VM on the env's private network runs integration or smoke tests against `*.railway.internal` without touching service containers. Destroy it afterwards. (sandboxes [F])
3. **`railway metrics --http --path … --json` before and after a deploy**: error rate and latency percentiles per path give a canary verdict with no app instrumentation. (cli/metrics [F])
4. **`railway logs --http --status ">=500" --since 10m --json` and `--network --status dropped` / `--dns --status failed`**: prove no 5xx, no dropped connections and no broken internal DNS after a change. (cli/logs [F])
5. **Healthcheck on `/readyz` as a deploy gate**, with `healthcheck.railway.app` allowed. The new version never takes traffic unless it answers 2xx within the timeout. (deployments/healthchecks [F])
6. **Throwaway environment**: `railway environment new exp-X --duplicate staging`, or the API with `skipInitialDeploys:true`. Seed data yourself. Delete it afterwards. (cli/environment, api/manage-environments [F])
7. **Tracing with a forced `traceparent`**: one synthetic request, followed through gateway → FastAPI → Postgres/Redis spans. `railway trace list --errors`. (observability/tracing [F])
8. **`railway config plan --detailed-exit-code`** in CI detects config drift between the repo and the live env. Exit 2 means drift. (infrastructure-as-code [F])
9. **Wait for CI**: Railway deploys only after all GitHub Actions workflows pass, which ties our preflight gates to the live deploy. (github-autodeploys [F])
10. **Webhooks → verifier service**: on `Deployment.*` success, run the smoke suite. Authenticate with a secret custom header. Reconcile via the API, since delivery is best effort. (observability/webhooks [F])
11. **Manual volume backup before experiments, plus reviewable restore**. For the official Postgres image, **PITR restore into a sibling service** allows zero-risk inspection of the past without touching prod. (volumes/backups, point-in-time-recovery [F])
12. **Edge rules gating debug and experiment endpoints** by secret header or office CIDR, together with `X-Railway-Debug` and `X-Railway-Request-Id` for request-level correlation. (networking/edge-rules, specs-and-limits [F])

Runner-up: rollback (image plus variables, within 120h on Pro) as the undo button for a bad experiment.

## Documented gotchas (silent breakers)

1. **Healthcheck is deploy-time only.** "Railway does not monitor the healthcheck endpoint after the deployment has gone live." Green deploys say nothing about the service an hour later. [healthchecks F]
2. **Healthcheck host is `healthcheck.railway.app`.** Host allow-lists (FastAPI TrustedHostMiddleware, nginx `server_name`) cause "failed with status 400" or "service unavailable". A wrong `PORT` with target ports has the same effect. [healthchecks F]
3. **Volume services can't overlap.** Postgres, Redis and NATS with volumes always have downtime on redeploy, even with a healthcheck. Image auto-updates also redeploy them. [healthchecks F, services F]
4. **Legacy environments (created before 2025-10-16) have IPv6-only private DNS.** A server bound to `0.0.0.0` is unreachable over `*.railway.internal`, and clients resolving A records get ENOTFOUND. [private-networking/how-it-works F; ENOTFOUND troubleshooting S]
5. **The private network does not exist at build time.** Migrations or health probes in `RUN` or the build command fail. [how-it-works F]
6. **Pre-deploy runs in a separate container with no volumes**, is not retried, and **has no timeout by default**, so a hung migration holds the deploy. [pre-deploy-command F]
7. **Deploy ordering is not applied to GitHub push deploys** (including monorepo multi-service pushes), so a service can boot before its Postgres or NATS dependency is ready. [deployment-actions F]
8. **Draining defaults to 0s.** The old deploy gets SIGTERM and is immediately killed, which drops in-flight HTTP requests and NATS acks. [deployments/reference, variables/reference F]
9. **Sealed variables are not copied** to PR, duplicated or synced envs, and are not given to `railway run`. Previews fail on missing secrets. [variables F]
10. **PR and duplicate envs copy prod variables.** A literal (non-reference) prod `DATABASE_URL` means the canary writes to prod data. [ship-on-merge-pr-canaries S]
11. **Networking changes skip staging**: they are applied immediately. [staged-changes F]
12. **Log rate limit is 500 lines/s per replica**; excess is dropped. No native log drain. Retention on Pro is 30 days. [logs F]
13. **Webhooks are unsigned, unordered and best-effort**, and are disabled for 24h after 100 failures in 6h. [webhooks F]
14. **Serverless**: the first request after sleep "may return a 502". Open DB pools and private traffic prevent sleep. The setting applies only after a redeploy. [serverless F]
15. **Cron**: a run still `Active` blocks later runs (they are silently skipped). Minimum 5 minutes. UTC. Imprecise by minutes. [cron-jobs F]
16. **Custom Postgres images (PostGIS) are excluded** from PITR, HA and one-click major upgrade. Manually bumping the major tag doesn't run `pg_upgrade` and "the database will very likely refuse to start". [postgresql-ha, postgresql-major-upgrade, point-in-time-recovery F]
17. **Backups**: wiping a volume deletes its backups. A backup restores only into the same project and environment. Manual backups are capped at 50% of the volume size. [volumes/backups F]
18. **Rollback window**: images are kept only 120h on Pro. After that only a rebuild-redeploy is possible. Rollback never restores volume data. [pricing/plans F]
19. **Config-as-Code hard cutoff on 2026-12-01.** `railway.json`/`railway.toml` stop being read. The IaC SDK drops `tracing`, so `apply` would disable tracing. [config-as-code, infrastructure-as-code/reference F]
20. **API authorization errors return HTTP 200** with an `errors[]` array, so a verifier that checks only status codes passes falsely. [integrations/api F]
21. **Monorepo watch paths**: with watch paths configured, empty commits don't redeploy. Skipped deploys are hidden until you click "Show Skipped". [github-autodeploys F]
22. **Wait for CI** skips the deploy after 2 hours, ignores non-Actions checks, and a cancelled workflow can let a deploy through if another workflow passed. [github-autodeploys F]
23. **`NEEDS_APPROVAL` is not a documented status.** The documented approval and CI-wait status is `WAITING`, and the "Deployment Approval" UI covers only pushes from GitHub users not linked to Railway. [manage-deployments, services F]
24. **Usage hard limit takes all workloads offline**, including prod in the same workspace. [cost-control F]
