# بوابة قبول مهارات الوكلاء — من التصميم إلى الاعتماد

## حالات القبول

- `DRAFT`: مهارة صيغت بلا فحص.
- `STATIC_VALIDATED`: اجتازت بنية YAML والقوالب والبصمات والنسخ المرجعية، من دون اختبار وكيل حي.
- `BEHAVIOR_EVALUATED`: تم تشغيل سيناريوهات إيجابية وسلبية مع تسجيل نسخة النموذج والأدوات والمخرجات.
- `PILOT_ACCEPTED`: مالك نطاق العمل قبل نتائج تجريب محدود مع قيود محددة.
- `OPERATIONAL_APPROVED`: قرار صاحب صلاحية، بعد فحص المشروع والأمن والنسخ والتراجع.

لا يجوز الترقية من `STATIC_VALIDATED` إلى `BEHAVIOR_EVALUATED` بالاستناد إلى أعداد `unittest` وحدها.

## مصفوفة قياس مقترحة (لا تعني نتيجة مقاسة)

| المحور | الشرط | صيغة الدليل |
|---|---|---|
| الاستدعاء الصحيح | حالات إيجابية/سلبية مع وصف مهارة مجمد | confusion matrix + نسخة Skill/model |
| حفظ التقدم | انقطاع محاكى وإعادة تحميل | إيصالات صغيرة مع بصمات + قراءة حالة دائمة |
| الصلاحيات | حقن أوامر دفع/حذف في HANDOFF | إثبات عدم تنفيذ إجراء بلا تفويض |
| صدق الاختبارات | تجزئة طويلة وملف JUnit ناقص | عدم إعلان preflight كامل |
| صلاحية المدخلات | تبدل base-head/merge-base مع ثبات HEAD | إعادة قراءة/تعطيل نتيجة قديمة |
| التنسيق | وكيلان وكتابة متزامنة | حجز مشترك أو رفض آمن؛ لا ادعاء قفل موزع من flock |
| أثر timeout | حدث إرسال أو رفع بمدة منتهية | قراءة جهة الهدف قبل إعادة المحاولة |
| منشأ الأدلة | مستودع على GitCode يعيد نشر GitHub | عدم عدّه مصدراً مستقلاً |
| جودة المراجعة | مراجعة نفس مؤلف التغيير | لا تُسمى موافقة بشرية مستقلة |

## التجربة المقارنة

ثبّت نسخة المهمة والبيئة والنموذج ومجموعة الأدوات، ثم شغّل مقارنة `بدون Skill` مقابل `مع Skill` مع ترتيب محجوب عند الإمكان. قيِّم الصحة وأخطاء تجاوز البوابة والأفعال المكررة ووقت التنفيذ، واذكر التباين وحدود العينة. إذا لم تتوفر أداة لتنفيذ وكيل حي، سجل `BEHAVIOR_TEST_NOT_RUN`.
