# دراسة مقارنة: المهارات المهنية للوكلاء وإدارة العمل الموثوق — 19 أكتوبر 2026

## 1) الحكم التنفيذي

**النتيجة:** لا توجد منصة أو حزمة Skills واحدة تضمن وحدها العمل الاحترافي، أو الحفظ الدائم، أو اختبارات القبول، أو تفويض الأفعال. الأكثر فاعلية هو الجمع بين **بروتوكول بسيط للاستئناف**، و**مهارات متخصصة حسب نوع المهمة**، و**مخرجات وأدلة قابلة للتحقق**، و**بوابات أعمال خارجية مستقلة**. هذه توصية معمارية مستنتجة من المقارنة، لا نتيجة قياس أداء على مشاريع المستخدم.

أُبقي UWRP Portable v3.1 وAdaptive Test Accelerator v1.1 كما هما (ZIPs ببصماتهما الأصلية)، وأضيف طبقة Professional Portable v4 التي تتعامل مع نواقص ما قبل الاختبار وما بعده: اختيار المهارة، تعريف النجاح، توثيق الأدلة، التقصي عن السبب، تنسيق الوكلاء، المراجعة، وتسليم الأعمال.

## 2) كيف تحققت من المصادر

- راجعت الأدلة **الأصلية** لمعيار Agent Skills، وGitHub Spec Kit، وOpenSpec، وAnthropic Skill Creator، وSuperpowers، وAgent Skills لعمليات التطوير.
- راجعت وثائق GitHub Actions وGitLab CI وGitee Go/PR من أصحاب الخدمات، إضافة إلى نماذج Skills على GitCode، مع تصنيف المرآة عن المصدر الأساسي.
- قارنت أنماط Temporal وLangGraph وPrefect للاستعادة والتنسيق مع احتياج prompt مستقل عن أدوات التنفيذ.
- استعنت بمرجع OWASP Agentic Top 10 2026 وOpenSSF Security Baseline في الحدود الأمنية.
- يحدد `SOURCE_REGISTER.json` روابط **38 مرجعاً** ونوعها، ولا تعني هذه الروابط أننا اختبرنا جميع المنتجات أو ادعاءات أصحابها. **لم يُجرَ تنفيذ حي لعمال هذه المنصات أو اختبارات مقارنة وكلاء مدفوعة في هذه الدراسة.**

## 3) المقارنة بين المشاريع والمناهج

| المصدر | ما يُوثّقه | ما سنستفيد منه | القيد المهم |
|---|---|---|---|
| Agent Skills open specification | `SKILL.md`، `name`/`description`، ملفات مساعدة وتحميل تدريجي | واجهة مهارة قابلة للنقل | مواضع التثبيت والتنفيذ تختلف باختلاف الوكيل |
| `anthropics/skills` Skill Creator | تقييم أمثلة بوجود Skill وبدونها وقياس الاستدعاء والنتيجة | مختبر جودة ومؤشر للمحفزات الخاطئة | لا تعني نتيجة اختبار البنية نجاح الوكلاء الحقيقيين |
| `obra/superpowers` | التفكير المنهجي، اختبار قبل التعديل، التحقق قبل إعلان الإنجاز | مهارة للتحقيق ومراجعة الادعاءات | بعض القواعد مطلقة أكثر من اللازم لأعمال غير برمجية؛ تُطبّق حسب الحالة |
| `github/spec-kit` | Specify → Plan → Tasks → Implement → Converge، وتحليل الاتساق | ربط مطلب ← مهمة ← دليل | تكلفة المواصفات التفصيلية لا تُفرض على مهمة بسيطة |
| `Fission-AI/OpenSpec` | إجراءات مرنة وفق الاعتماديات، دون إجبار الجميع على مراحل ثابتة | العودة للتصميم إذا ظهرت أدلة جديدة | التغييرات في العقود تحتاج إثباتاً مستقلاً |
| `addyosmani/agent-skills` | مسار DEFINE/PLAN/BUILD/VERIFY/REVIEW/SHIP، ومهارات صغيرة | تقسيم المهارات بحسب المسؤولية | مهارة عالمية واحدة تستهلك السياق بلا حاجة |
| `agentsmd/agents.md` | ملف موجّه للوكيل يحمل قواعد المشروع | محول اختياري لقواعد المستودعات | AGENTS.md ليس مصدر تفويض أعلى من المستخدم/السياسات |
| Temporal | Event History، إعادة المحاولة وidempotency | السجل الحقيقي يجب أن يكون قابلاً للاستعادة | Prompt وحده لا ينفذ replay ولا يقدم exactly-once |
| LangGraph | Checkpointers وحالة على مستوى تنفيذ Graph | فصل نقطة الاستعادة عن الحالة الممتدة | يلزم دعم تخزين حقيقي، وليس نص HANDOFF فقط |
| Prefect | حدود تزامن عامة ومخازن نتائج | إدارة موارد عمل متعددة | لا تضمن المهارة قيوداً خارج نطاق الموفر |

**قرار التصميم:** نستعير الأنماط المعروفة دون نسخ كود خارجي أو فرض إطار تشغيل خاص. لا ندّعي اختبارها على جميع أنظمة المستخدم.

## 4) المقارنة بين منصات استضافة الكود

| المنصة | الميزات الموثقة المفيدة | التطبيق المرن | حدود الثقة |
|---|---|---|---|
| GitHub | Actions `concurrency` وreusable workflows وartifact attestations | حصر تشغيلات المستودع، تقليل تكرار YAML، إثبات منشأ بناء عند توفر الخدمة والتحقق منه | التزامن ليس قفلاً عابراً لكل الخدمات؛ بعض ميزات attestations مرتبطة بالخطة/الرؤية |
| GitLab | `resource_group`، `needs` DAG، `rules:changes:compare_to`، `cache:key:files`، JUnit report | فصل الموارد الحساسة عن الأعمال المتوازية وتشغيل التغييرات المتأثرة | JUnit لا يجعل المهمة تفشل تلقائياً: يلزم exit code غير صفري؛ تقييد الملفات/العدد |
| Gitee | Gitee Go YAML pipeline ومعرّف، بوابة PR مع حماية الفروع، Fork+Pull | تعيين محول لتنفيذ قواعد الجودة والتعاون | قد تسمح سياسة المستودع بتجاوز إداري؛ ليست كل الإمكانات متاحة على كل خطة |
| GitCode / AtomGit | صفحات مشاريع SKILL.md وأمثلة DevOps ومرايا مشاريع | اكتشاف أنماط وتوافق تخزين الكود | لا نعدّ المحتوى المنسوخ دليلاً مستقلاً؛ نتحقق من upstream/الترخيص/commit |

**التوصية:** تُعرّف خطة العمل العامة `required_gates` و`source_version` و`action_authority` محايدة، ثم يترجم محوّل موفر واحد فقط هذه المتطلبات إلى أدواته؛ لا نضع GitHub YAML في صلب Skills، ولا ننسخ بوابات Gitee إلى GitLab دون مراجعة التكافؤ.

## 5) ثمانية تحسينات مباشرة على المنظومة السابقة

### P0 — واجبة قبل التوسع

**P0-1 اكتشاف المهارة الصحيح:** لا يحمل الوكيل الحزمة كاملة مع كل سؤال. Router يطابق مشغّل المهمة بمهارة صغيرة، ويختبر مهارات محددة وأمثلة **عدم التشغيل**. نوصي أن تكون `SKILL.md` قصيرة ولها trigger قابل للفحص.

**P0-2 تعريف النجاح قبل التنفيذ:** Work Contract مصغر يتضمن الغرض، المستثنيات، حدود الصلاحيات، شروط القبول، مصدر الحقيقة ودليل كل مطلب. يخفف الادعاءات العامة وعمليات «إغلاق فجوات» دون برهان.

**P0-3 صلاحية كل دليل:** إدراج source-version + base-head + merge-base **عند انطباق Git**؛ أو مراجعات المستندات وتواريخ المصدر للبحث؛ وفي الأنظمة الحية لا يعاد استخدام صورة حالة متقادمة. تقاس validity بحسب المدخلات المؤثرة، لا كل مدخلات العالم.

**P0-4 حدود الصلاحية والأفعال الخارجية:** لا تمنح Skill صلاحية دفع/دمج/نشر. يُسجل action ID ويُراجع النظام الهدف قبل إعادة فعل بعد timeout. الاستراتيجية مستوحاة من at-least-once retries لدى Temporal، وهي لا تمنح exactly-once بلا بنية داعمة.

### P1 — تسريع وتحسين الجودة

**P1-1 مراجعة مستقلة بمقاييس:** لكل تغيير نسخة دقيقة، ونطاق، ومخاطر، وnegative control عند الإمكان، ونتائج فحوص ذات إسناد. لا تُسمى مراجعة وكيل مستقل عن الكاتب *قبولاً بشرياً*.

**P1-2 جداول مهام موجّهة بالاعتماديات:** تشغّل الاختبارات الحرجة مبكراً حيث يسمح DAG بذلك؛ تقتصر `concurrency` على مورد واضح، وتبقى قاعدة البيانات الثقيلة تسلسلية عند انخفاض الموارد. اختبارات محددة للتغذية الراجعة، والبوابات الواجبة للقبول.

**P1-3 مختبر Skills ضد المحفزات والتجاوز:** نقارن مع/بدون المهارة على نفس السيناريو (إمكان الاختبار الفعلي شرط)، ونقيس أخطاء استدعاء المهارة، الادعاءات بلا دليل، حوادث إعادة الأفعال، والوقت/الكلفة. تُسجّل نتائج اختبارات القوالب محلياً مع فصلها عن اختبار السلوك الحي.

**P1-4 فصل معمارية التنسيق عن prompts:** لكل وكيل ملكية واضحة للمورد والتسليم؛ القفل المحلي لا يرى السحابة، وref حجز لا يكفي لفصل عامل قديم؛ عند الحاجة نستخدم backend lease/fencing. عدم ضمان الحصرية يعني عدم تشغيل كتابات متزامنة.

### P2 — اختيارية لأعمال تستحق التكلفة

اعتماد Temporal أو LangGraph أو Prefect للمشاريع التي تتطلب استئنافاً تشغيلياً حقيقياً بين الحاويات والأجهزة. لا داعي لترحيل جميع أعمال الكتابة أو التحليل إليها.

## 6) تحذيرات ثبتت في الوثائق الأصلية

- `GitLab` يذكر صراحة أن تقارير JUnit تُظهر النتائج لكنها لا تجعل المهمة تفشل: يفصل `exit code` بين الدليل والحكم.
- `Playwright` يتيح تقسيم الملفات أو الحالات حسب `fullyParallel`؛ ينبغي التحقق من اكتمال وحدات الاختبار قبل قبول التقرير المدمج.
- `GitHub Actions` يحصر `concurrency` في مجموعة داخل المستودع، ولا يثبت التزامن بين الحاويات المستقلة.
- `Gitee` توفر PR Gates، لكنها تذكر إمكان تجاوز الحظر للإداري؛ لا يفترض البروتوكول أنها غير قابلة للتجاوز.
- `OpenAI Agents SDK` يفرق بين guardrails أول سلسلة الوكلاء وحواجز الأدوات؛ لا يكفي نجاح فحص أولي لحماية كل الأفعال.
- `OWASP` يعامل prompt injection وأذونات الأدوات والثقة الزائدة من مخاطر الوكلاء؛ ملفات Skills وحالة الاستئناف ومدخلات البحث غير الموثوقة ليست تعليمات عليا.

## 7) معايير قياس التحسن: لا أرقام من دون baseline

| المعيار | كيفية قياسه | ما لا يثبته |
|---|---|---|
| زمن الإنجاز `wall_clock` | نفس مهمة/نفس بيئة/تفاوت موثق قبل وبعد | لا يقيس جودة الناتج وحده |
| نسبة العمل المعاد بعد الانقطاع | وحدات أعيد تنفيذها / وحدات صالحة مكتملة | لا يثبت سلامة النسخ الاحتياطي |
| فوات الاختبارات | Missing IDs مقارنة بالجرد المجمد | لا يثبت مطابقة المتطلبات |
| false-trigger | مهارات تم تحميلها رغم عدم ملاءمتها / الحالات السلبية | لا يثبت مهارة لم تعمل |
| Evidence closure | متطلبات لديها دليل مطابق / جميع المتطلبات | لا يعني قبولاً إنتاجياً |
| التأثيرات المكررة | أفعال خارجية مكررة تم التحقق منها | غياب رصد لا يعني الصفر |
| source originality | ادعاءات ذات إسناد upstream / جميع الادعاءات | لا يعني صحة الاستنتاج |
| مراجعة الصلاحيات | أفعال مؤثرة مقيدة بتفويض مثبت / إجمالي الأفعال | لا يعادل قرار المالك |

القياس يجب أن يكون **على أزواج مهام متماثلة**، بعد تدوين اختلاف النموذج والأداة وإصدار النص؛ لا ننسب فرق الوقت إلى المهارة إذا تغيرت الآلة أو المدخلات أو نطاق الاختبار.

## 8) خطة التطبيق الآمنة

**المرحلة A — قرائية فقط:** تشغيل Router وResearch وChange Review في بيئة بلا أدوات تعديل، على أمثلة صناعية ومهام حقيقية غير حساسة. مراجعة الالتزام بحدود المصادر، وقياس false triggers.

**المرحلة B — مشروع تجريبي:** تفعيل Intent-to-Proof وFailure Investigation مع مصدر بيانات تجريبي واختبارات ذات أثر موثق. لا تغيير في بوابات المشروع.

**المرحلة C — مهارة تنسيق ومخرجات:** تجربة تعيين مهام لوكيلين في موارد منفصلة، ثم سيناريو تعارض مقصود وتحليل السلوك؛ لا يُعلن ضمان تنسيق موزع دون lock backend.

**المرحلة D — تسليم خاضع للسياسة:** استخدام Safe Delivery بعد الحصول على التفويض وبوابات المشروع والمراجعات؛ البدء بإجراء قابل للعكس ثم سيناريو تعطل محاكى. لا دمج ولا نشر تلقائياً لمجرد تثبيت Skill.

**بوابة التعميم:** اختبار هيكلي PASS + مقارنة سلوكية حقيقية موثقة + مراجعة أمنية مستقلة + تحقق توافق كل بيئة + موافقة المالك. إذا لم تتوفر اختبارات الوكيل الحقيقية، يبقى التوصيف `DESIGNED_AND_STATICALLY_VALIDATED`.

## 9) أمثلة عملية للتفعيل

- «تابع من آخر نقطة توقف» → work-router ثم UWRP baseline؛ استئناف الدليل بعد التحقق.
- «اختبارات CI بطيئة» → adaptive-test-accelerator؛ الجرد ثم خطة تنفيذ جزئية صالحة.
- «ابحث أفضل حلول Redis Streams / Gitee / GitLab» → evidence-research؛ تمييز الأصل والمرايا.
- «جهز خطة إصلاح شاملة» → intent-to-proof + failure-investigation بحسب العطل.
- «راجع PR قبل الدمج» → change-review ثم safe-delivery **فقط** بعد طلب فعل وتنفيذ الشروط.
- «هناك وكيل يعمل على نفس الفرع» → collaboration-coordination؛ إيقاف الكاتب الثاني حتى حل الملكية.
- «طور Skill جديدة» → skill-evaluator؛ أمثلة إيجابية وسلبية، مقارنة بغياب المهارة.
- «اكتب رسالة قصيرة» → LIGHT مباشرة، دون ملفات حالة أو أغلفة اختبار.

## 10) حدود وثوابت

هذه الحزمة **لا** تثبت تحسيناً مقيساً في مشاريع المستخدم، ولا تعد بتشغيل تلقائي عبر كل وكلاء الذكاء الاصطناعي، ولا تمنح امتيازات، ولا تستبدل موافقات النشر والدمج. المصدر المحفوظ في مكتبة ChatGPT مرجع يمكن طلب استدعائه، وليس تثبيتاً عاماً في Codex/Claude/Kimi. يمكن تفعيلها نصياً بلا برامج، أو تثبيتها كمهارات حيث تسمح بيئة الوكيل بذلك.

> قائمة المصادر الأصلية، ونوع الوثيقة، وتاريخ البحث، موثقة في `SOURCE_REGISTER.json`. استخدم الروابط لقراءة آخر إصدار عند اتخاذ قرار تشغيلي؛ ليست نتيجة البحث لقطة حية دائمة.
