# حتميّة إعادة البناء (Replay Determinism) — مراجعة #2

## التحذير الذي احترمتُه أوّلاً
المراجعة حذّرت من "micro-governance sprawl" (guards فوق guards). **لم أضِف
أيّ حارس جديد**. ركّزتُ على فحص المنطق الموجود وإصلاح عيب حتميّة حقيقي.

## العيب الحقيقي المكتشف (#2)
FieldStateReconstructor.reconstruct يرتّب الأحداث بـoccurred_at فقط. اختبرتُ:
- ترتيب إدخال مختلف لأحداث بأوقات **مختلفة** → حتمي ✓ (كان سليماً)
- لكن أحداث بـoccurred_at **متساوٍ** → عكس الإدخال يغيّر النتيجة (20 vs 10)
  **غير حتمي** — وهذا خطير: replay قد يعيد بناء حالة مختلفة لنفس الأحداث.

## الإصلاح (سطر واحد، لا طبقة)
sort key أصبح: (occurred_at, seq, event_id) — tiebreaker مستقرّ. يطابق نموذج
السلطة الزمنيّة (TEMPORAL_AUTHORITY: occurred_at + seq) الذي بنيناه سابقاً.
الآن: occurred_at متساوٍ → seq يحسم → حتمي دائماً.

## الإثبات
- ترتيب إدخال مختلف (يحاكي clock skew/reconnect/late replay) → نفس الحالة ✓
- occurred_at متساوٍ + seq → 20==20 (حتمي، لا اعتماد على ترتيب الوصول) ✓
- إعادة البناء متكرّرة → idempotent ✓

## ما لم أفعله (احتراماً لتحذير المراجعة + حدود الساكن)
- ❌ لا حارس/طبقة جديدة (تجنّب micro-governance sprawl)
- البنود الأخرى (#1 clock skew الحيّ، #3 memory soak، #4 migration rehearsal،
  #5 human failure) **تحتاج تشغيلاً حيّاً** — لا تُحسَم ساكناً. اختبرتُ المنطق
  النقي (replay) الذي يمكن إثباته الآن؛ الباقي على جهازك.
