# تدقيق المراجعة التأمّليّة — ما نُفّذ وما لا يُنفَّذ بكود

هذه المراجعة تقييم تأمّلي (تتّفق مع النهج، تطرح أسئلة استراتيجيّة). دقّقتُ
نقاطها وميّزتُ بصدق بين القابل للتنفيذ والاستراتيجي.

## ✅ فجوة حقيقيّة أُصلحت: Observability للخطّ الجغرافي (#7)
المراجعة محقّة جزئيّاً: البنية (prometheus/grafana/otel) موجودة، لكنّ خدمات
التطبيق لم تكن تعرّض /metrics، وprometheus لم يكن يلتقطها (black-box جزئي).
**الإصلاح**: 
- raster /metrics بتنسيق Prometheus (حالة المهامّ، النشطة، الطبقات) — بلا
  تبعيّة ثقيلة (نصّ exposition)
- prometheus.yml يلتقط sahool-raster-service الآن
صدق: مقاييس مشتقّة من _jobs الفعليّة، لا مخترعة.

## ⚠️ نقطة #8 (disaster للأصول): مُجابة أصلاً بالتصميم
المراجعة تسأل: هل النواتج المشتقّة canonical أم reproducible؟ تحقّقت:
raster_provenance.py يحمل scene_id + capture_datetime + formula_version +
provenance_hash → **النواتج reproducible لا canonical** (نفس المدخلات = نفس
البصمة). إجابة المراجعة موجودة في التصميم: لو فُقد NDVI، يُعاد بناؤه من
المشهد + الصيغة. هذا التصميم الصحيح أصلاً.

## 🔴 الأسئلة الاستراتيجيّة (لا تُحَلّ بكود — وأرفض التظاهر بذلك)
المراجعة تطرح بصدق: 
- geospatial-first أم GIS-enabled؟
- Platform Identity Diffusion (ما المنتج الأساسي؟)
- tile generation strategy (pre-gen / server-side / regional)
- edge strategy / regional replication / spatial event lineage

**هذه قرارات منتج/معماريّة تحدّد أولويّات سنة.** المراجعة نفسها تثني على
الجملة: "أخطر ما أفعله هو التظاهر بحلّ سؤال استراتيجي بـcommit." ألتزم بذلك:
لن أكتب كوداً يدّعي حسم هذه الأسئلة. هي حوارك أنت.
