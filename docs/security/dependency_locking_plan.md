# SEC-6 — Dependency Locking Plan (خطّة تثبيت التبعيّات)

> النطاق الآمن (SAFE scope). زيادة غير كاسرة الآن + خطّة مرحليّة للباقي.
> المصادر: `CLAUDE.md` (قاعدة pip-audit-قبل-التعديل) · `.github/workflows/ci.yml`
> (بوّابة *Security Scan*) · مسح المستودع 2026-07-02.

## 1. المشكلة (VERIFIED)

مسحُ كلّ ملفّات `requirements*.txt` تحت `services/ bots/ agents/` +
`requirements_real.txt` (28 ملفّاً، 219 مواصفة) أظهر:

| الحالة | العدد |
|---|---|
| مثبّت بدقّة (`==`) | 93 |
| مدَى/غير مثبّت (`>=`, `^`, بلا قيد) | **126** |

(العدّ التقريبيّ ~157 في التقرير الأصليّ يشمل صيَغ `^`/غير-txt في مصادر أخرى؛
العدّ أعلاه هو ما يقيسه هذا الريبو فعليّاً على ملفّات `requirements*.txt`.)

**الخطر:** انحراف البناء (build drift) — تثبيتان في وقتين مختلفين قد يجلبان
إصدارات مختلفة، فيختلف سلوك الإنتاج عن التطوير، وقد تتسلّل ترقية ثانويّة تحمل
ثغرة دون مراجعة. سابقة واقعيّة: `python-multipart` 0.0.27 حملت CVE فحجبت CI حتى
ثُبّتت عند `0.0.31` (CLAUDE.md).

## 2. لماذا لا نقفل كلّ شيء دفعة واحدة

قفلٌ كاملٌ فوريّ (`==` لكلّ حزمة عبر 28 ملفّاً) قد يُظهر **تعارضات توافق حقيقيّة**
بين خدمات تشترك قيوداً متباينة (مثال محسوس: `redis` مثبّت `==5.3.1` في
sahool-platform بينما يحلّه المُحلِّل بحُرّيّة إلى `8.0.1` في auth). دفعُ ذلك دفعةً
واحدة يخاطر بكسر تثبيتات CI عبر خدمات كثيرة ويستوجب تراجعاً مكلِفاً — وهو
عكس هدف الشريحة. لذا نُثبّت **تدريجيّاً وبتحقّق pip-audit لكلّ ملفّ**.

## 3. المسار الحرج (الأولويّة القصوى)

الملفّات الأربعة التي **تحجب** بوّابة pip-audit الدمجَ عليها في CI
(`ci.yml` → *Security Scan* → «pip-audit (gating — critical path)»):

| الملفّ | مثبّت `==` | غير مثبّت |
|---|---|---|
| `services/sahool-platform/api/requirements.txt` | 14 | 2 (`anthropic`, `asyncpg`) |
| `services/auth/requirements.txt` | 3 | 8 |
| `services/guardrails-engine/requirements.txt` | 3 | 8 |
| `requirements_real.txt` | 3 | 12 |

## 4. المُسلَّم الآن (SEC-6، غير كاسر)

1. **حارس سقّاطة**: `tests_v9/test_requirements_pinning_guard.py` (مُعلَّم `unit`،
   مسح ملفّات صرف — لا يستورد fastapi). أخضر اليوم، يمنع الانحدار فقط:
   - لا يُفكّ تثبيت أيّ حزمة مثبّتة اليوم بـ`==` على المسار الحرج.
   - لا يزيد عدد الحزم غير المثبّتة لأيّ ملفّ حرج عن خطّ الأساس (2/8/8/12).
   - إطار العمل النواة (`fastapi`/`uvicorn`/`pydantic`) على **نفس** الإصدار عبر
     الملفّات الأربعة (يمنع انزلاق إصدار الإطار).
2. **هذه الوثيقة**: خطّة القفل المرحليّ.

**لم تُعدَّل أيّ `requirements.txt` وقت التشغيل** — صفر خطر كسر تثبيت CI.

## 5. الأدوات (verified 2026-07-02)

- `uv 0.8.17` **متوفّر** ويحلّ عبر الوكيل: `uv pip compile services/auth/requirements.txt`
  ينجح ويُنتج قفلاً كامل الشجرة العابرة.
- `pip-compile` (pip-tools) غير مثبّت؛ `uv pip compile` بديله المباشر.
- `pip-audit 2.10.1` متوفّر.

**سببُ عدم تسليم ملفّات `.lock` مُولَّدة الآن (قرار مقصود):** الحلّ الحرّ يثبّت
**أحدث** الإصدارات (مثلاً `redis==8.0.1`، `starlette==1.3.1`) التي تنحرف عن
الإصدارات المُختبَرة/المثبّتة في ملفّات شقيقة على المسار الحرج (`redis==5.3.1`).
التزام قفلٍ يوجّه «التثبيت-من-القفل» في الإنتاج إلى قفزة إصدار رئيسيّة غير
مُختبَرة = بالضبط الكسر الذي يحذّر منه نطاق الشريحة. لذا يُؤجَّل توليد الأقفال إلى
تنفيذ مرحليّ مضبوط بالقيود (أدناه).

## 6. الخطّة المرحليّة (لكلّ ملفّ حرج)

لكلّ ملفّ، بالترتيب، مع تحقّق pip-audit إلزاميّ (CLAUDE.md):

```bash
# 1) ثبّت المدَيات المفتوحة على إصداراتها المُختبَرة حاليّاً (لا قفزات رئيسيّة):
#    استخرِج الإصدار المُثبَّت فعليّاً في بيئة CI/الحاوية ثمّ حرّره إلى ==.
# 2) ولّد قفل الشجرة العابرة بقيود متّسقة عبر الخدمات المتشاركة:
uv pip compile <service>/requirements.txt -o <service>/requirements.lock \
    --constraint constraints/shared.txt      # يُثبّت redis/asyncpg/... موحّداً
# 3) بوّابة CLAUDE.md — لا ثغرة جديدة:
pip-audit -r <service>/requirements.lock --progress-spinner off
# 4) في الإنتاج، ثبّت من القفل:  pip install -r <service>/requirements.lock
```

الترتيب المقترح (الأعلى قيمةً أوّلاً): `auth` → `guardrails-engine` →
`sahool-platform/api` → `requirements_real.txt`. عند تثبيت كلّ ملفّ:
- وسّع `BASELINE_PINNED` وخفّض `BASELINE_UNPINNED_MAX` في حارس السقّاطة كي
  يقفل المكسب ولا يعود الانحراف.
- شغّل `pytest -m unit -k pinning_guard` للتأكّد من الخُضرة.

## 7. الواجهة الأماميّة (frontend) — مقفولة فعليّاً، لا تغيير

`frontend/package.json` يستخدم مدَيات، لكن `frontend/package-lock.json` موجود
و CI يستخدم `npm ci` (`.github/workflows/ci.yml:126,143`) — و`npm ci` يثبّت
**حصريّاً** من ملفّ القفل ويفشل عند أيّ تعارض. إذن Node مقفول فعليّاً؛ **لا حاجة
لأيّ تغيير** ضمن SEC-6.
