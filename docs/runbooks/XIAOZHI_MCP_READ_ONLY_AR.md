# ربط أدوات سهول المقروءة بخلفية Xiaozhi

## ما يقدمه هذا المسار

يضيف المحوّل المشترك دورة `initialize` ← `notifications/initialized` ← `tools/list` / `tools/call` إلى واجهات الأدوات القائمة. النسخة الوحيدة المعلنة هي **MCP 2025-06-18**، والنقل هو Streamable HTTP باستجابات JSON، وهو أحد الشكلين المسموحين في المواصفة. يُستعمل `httpx.ASGITransport` للنداء الداخلي، المتوافق مع HTTPX 0.28، ويعيد كل نداء المرور على مصادقة واجهة REST الأصلية.

هذا طرف HTTP للأدوات السحابية، وليس خادم بروتوكول الصوت الخاص بلوحة Xiaozhi. غلاف الجهاز `type: "mcp"` فوق WebSocket/MQTT وإصدار الجهاز `2026-07-28` ليسا هذا النقل. عند إبقاء الصوت في خلفية Xiaozhi المختارة لا يحتاج ربط الأدوات إلى تحويل Opus أو LiveKit؛ على الخلفية أو جسرها دعم HTTP 2025-06-18 وتمرير اعتماد مستخدم سهول المسموح. إذا أعاد `initialize` نسخة لا يدعمها العميل، يتوقف العميل عن الربط.

## الخدمات والتفويض

كل خدمة تعرض `/mcp/v1/stream` داخل حاويتها القائمة:

| الخدمة | النطاق المطلوب في رمز سهول | الأدوات المعروضة عبر HTTP |
|---|---|---|
| Weather | `weather:read` | قائمة أدوات الطقس الحالية |
| WOFOST | `crop:read` | قائمة أدوات المحصول الحالية |
| Sentinel | `satellite:read` | قائمة أدوات المشاهد/المؤشرات الحالية |
| Market | `market:read` | `get_market_price` و`get_price_trend` فقط |
| Context | `mcp:context:read` | قائمة خدمة السياق المحددة في `MCP_SERVICE` |

أدوات شراء المدخلات وإعلانات البيع والعقود الآجلة لا تظهر في سطح Market هذا، ويرفض المحوّل استدعاءها المباشر **حتى مع رمز admin**. تبقى واجهات السوق الأصلية وصلاحياتها منفصلة. مخطط `inputSchema` وصف للمدخلات؛ المصادقة وتحقق المدخلات الفعليان في المعالج الأصلي يظلان نافذين.

الاعتماد هو Bearer صادر من جهة سهول المعتمدة ويطابق سياسة JWT القائمة (issuer/audience/expiry/scopes/tenant). لا ينشئ المحوّل هوية خدمة ذات امتيازات ولا يحوّل MAC اللوحة إلى مستخدم. هذا المسار لا يضيف خادم تسجيل OAuth أو تدفق موافقة جديداً؛ يهيئ المشغل الخلفية التي تدعم اعتماد المستخدم وفق السياسة الحالية. لا تُنسخ أسرار HS256 أو مفاتيح توقيع سهول إلى الجهاز أو خلفية خارجية.

يُشتق المستأجر من الرمز المتحقق، ويُرفض `arguments.tenant_id` المخالف. لا تُمرر ترويسات العميل `X-Tenant-Id` أو `X-Agent-Token` أو `Host` إلى النداء الداخلي. تُرسل Authorization الأصلية فقط، وتُفرض صلاحية المجال مجدداً في المعالج. لا تُستخدم معرّفات JSON-RPC كمفاتيح تنفيذ أو منع تكرار.

## التهيئة واختبار العقد

1. اختر الخدمات والبيانات المرخص للخلفية قراءتها. تبقى معاملة الصوت وحفظه لدى الخلفية المختارة؛ ربط الأدوات لا يغير هذه الحقيقة.
2. قدم خدمة HTTP خلف HTTPS وتفويض الشبكة المناسبين. لا تضف منفذاً عاماً تلقائياً إلى Compose ولا تجعل خدمة داخلية مكشوفة اعتماداً على اسم MCP.
3. عميل خادم إلى خادم لا يحتاج `Origin`. كل Origin مرسل يُرفض افتراضياً. عند الحاجة ضعه كاملاً ضمن `MCP_ALLOWED_ORIGINS`، مفصولاً بفواصل، مثل `https://voice-console.example`. المطابقة للقيمة المهيأة، وليست مشتقة من Host. هذا الضبط لا يضيف CORS أو يمنح صلاحية بيانات.
4. أرسل `Authorization: Bearer ...` و`Content-Type: application/json` و`Accept: application/json, text/event-stream` مع كل POST. لا تسجل قيمة الرمز في المخرجات أو وثائق التشغيل.
5. ابدأ بهذا الجسم، بدون ترويسة نسخة قبل التفاوض:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "initialize",
  "params": {
    "protocolVersion": "2025-06-18",
    "clientInfo": {"name": "sahool-xiaozhi-tool-bridge", "version": "1.0"},
    "capabilities": {}
  }
}
```

تحقق من `result.protocolVersion`، ثم أرسل `MCP-Protocol-Version: 2025-06-18` على كل رسالة لاحقة. إشعار `notifications/initialized` بلا `id` يعيد HTTP 202 وجسماً فارغاً. اكتشاف الأدوات:

```json
{"jsonrpc":"2.0","id":2,"method":"tools/list"}
```

مثال قراءة سعر بعد اكتشاف أدوات Market:

```json
{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"get_market_price","arguments":{"crop":"wheat","market":"sanaa"}}}
```

النتيجة تحافظ على بيانات المصدر؛ لا تحول عدم وجود قراءة أو `verified=false` إلى واقعة موثقة. لا تنطق نجاح استشارة أو سعر بوصفه نجاح عملية شراء أو ري.

## الحدود المقصودة

- المحوّل stateless: لا يصدر `Mcp-Session-Id` ولا يحتفظ بتقدم الجلسة بين الطلبات. على العميل إرسال التهيئة والإشعار بالترتيب؛ يُتحقق من النسخة المعطاة في كل طلب. نسخة غائبة بعد التهيئة أو غير مدعومة تُرفض بـ400.
- لا يرسل طلبات أو إشعارات من الخادم. GET وDELETE يعيدان 405 بعد فحص الاعتماد وOrigin؛ لا توجد قناة SSE طويلة أو استعادة أحداث أو ضمان إلغاء طلب جار.
- كل القائمة صفحة واحدة، ولا يصدر cursor؛ cursor وارد غير معروف يُرفض. كل طلب JSON-RPC فردي وبترميز UTF-8؛ لا توجد دفعات.
- حد الجسم 64 KiB، ومهلة قراءة الجسم/نداء الأداة 30 ثانية افتراضياً. لا يعاد استدعاء الأداة تلقائياً عند المهلة أو انقطاع الرد. طلب `tools/call` بلا معرّف يُرفض ولا ينفذ كإشعار.
- استجابات 4xx/5xx الداخلية لا تُغلّف كنجاح. أخطاء المزود لا تكشف نص الاستثناء أو بيانات الاعتماد؛ `isError` الصريح يبقى خطأ أداة.
- هوية المستأجر في النقل لا تستبدل تحقق ملكية الحقل في خدمة البيانات. أداة IoT تستخدم المصدر الذي يحدده تنفيذ `owner_telemetry`؛ بقية أغلفة Context التي تكرر مدخلات المستخدم تظل `verified=false`، وليست رصداً حياً.

## تهيئة أداة IoT ومصدر القراءة

خدمة `sahool-iot-mcp` في `docker-compose.rag-kg-mcp.yml` تضبط صراحة:

```text
MCP_SERVICE=iot
PLATFORM_API_URL=http://sahool-platform:8000
```

العنوان هنا اتصال داخلي بمالك البيانات داخل شبكة Compose القائمة. عند تشغيل الخدمة خارجها، يضبط المشغل `PLATFORM_API_URL` إلى أصل Platform الصحيح دون مسار أو query أو بيانات اعتماد؛ العنوان الخارجي يتطلب HTTPS. العنوان غير المهيأ أو غير الصالح يجعل readiness لخدمة IoT ترفض الجاهزية. هذا فحص إعداد، ولا يثبت وصول الشبكة أو صلاحيات مستخدم معين.

يحتاج رمز المستخدم نطاق `mcp:context:read` لاجتياز مدخل MCP، كما يحتاج صاحبه صلاحيتَي `FIELD_VIEW` و`DEVICE_VIEW` لدى Platform. تمرر أداة IoT الاعتماد نفسه إلى المالك؛ لا تستبدله برمز خدمة أوسع ولا تكتفي بمعرف الحقل في كلام المستخدم.

### مفاتيح التحقق للخدمات الست

كل خدمة Context في overlay (`field/lab/satellite/iot/rag/knowledge-graph`) تتلقى `JWT_PUBLIC_KEY` و`SAHOOL_ENV`. يتطلب Compose أن يكون `JWT_PUBLIC_KEY` موجودًا وغير فارغ بصيغة `${JWT_PUBLIC_KEY:?...}`، فيرفض إنشاء إعداد الخدمة إذا غاب؛ المفتاح يجب أن يكون **المفتاح العام PEM الموافق لمُصدر رموز سهول RS256**. قدّم القيمة متعددة الأسطر من إعداد المشغل أو إدارة الأسرار، مع الحفاظ على فواصل أسطر PEM. لا يولد الملف مفتاحًا ولا يحتوي اعتمادًا افتراضيًا.

اضبط `SAHOOL_ENV=production` للنشر الإنتاجي. افتراضي overlay عند غياب المتغير هو production؛ وإذا كانت `.env` المنسوخة من مثال التطوير تضبط development فهي قيمة صريحة تغلب الافتراضي. في الحالتين وجود المفتاح العام يفرض RS256 في وسيط OAuth القائم. يبقى توافق المفتاح مع المُصدر وصلاحية الرمز وشبكة الخدمات شرطًا لا يثبته مجرد وجود متغير غير فارغ.

لا يوزع هذا overlay `JWT_SECRET` أو `JWT_PRIVATE_KEY` أو تجاوز `SAHOOL_ALLOW_HS256_IN_PROD` على خدمات Context. هذا حد تحقق بالمفتاح العام فقط؛ بيئة تعتمد رموز HS256 محلية تحتاج تهيئة مُصدر ومستهلك متوافقين قبل تشغيل هذا overlay، ولا تُعالج بإضافة سر توقيع مشترك إلى كل خدمة. لا يتغير منطق OAuth في هذه الرقعة، ولا تُنسخ مفاتيح توقيع سهول إلى لوحة Xiaozhi أو خلفيتها. إعدادات الخدمات الأربع في `docker-compose.v9.yml` مستقلة عن هذا التوسيع وتحتفظ بعقدها القائم.

مثال طلب بعد اكتشاف `get_sensor_signal`:

```json
{"jsonrpc":"2.0","id":4,"method":"tools/call","params":{"name":"get_sensor_signal","arguments":{"field_id":"field-001","device_id":"sensor-001","sensor_type":"soil_moisture"}}}
```

المدخلات الثلاثة معرفات فقط. تُرفض `value` أو `soil_moisture` أو أي قراءة مزعومة في arguments. يقرأ التنفيذ `/api/v1/me`، ثم الحقل، وقائمة الأجهزة، وآخر 100 قراءة للجهاز، ثم يعيد فحص ربط الجهاز بالحقل. هذه نافذة حديثة محدودة؛ غياب نوع الحساس منها يعيد `unavailable` وقيمة `null`، لا صفرًا ولا ادعاء بعدم وجوده تاريخيًا. تُعرض القراءة المتقادمة بوصفها `stale` مع وقتها ووحدتها وعمرها.

دلالة مصدر القراءة محددة: `source_verified: true` تعني أن الجواب جاء من مالك بيانات سهول بعد تفويض المستخدم؛ تظل `verified: false` و`decision_authority: none` و`governing: false`. لا يثبت ذلك معايرة الحساس أو سلامة القياس فيزيائيًا. كذلك `field_binding: current_device_binding_not_measurement_binding` يصرح بأن الربط هو ربط الجهاز الحالي؛ لا ينسب قياسًا تاريخيًا إلى الحقل وقت تسجيله إذا انتقل الجهاز بين الحقول. يجب الحفاظ على هذه الدلالات عند عرض الجواب أو نطقه.
