# تقوية الfirmware — replay window + watchdog

المراجعة محقّة: `lastCmdTs` كان "minimal viable dedup". قوّيتُه لمستوى إنتاجي.

## ١. نافذة الإعادة (replay window) — بدل المعرّف الواحد
**كان**: `lastCmdTs` يحفظ آخر طابع زمني فقط → يكتشف التكرار **المتتالي** فقط.
المشكلة: تسليم MQTT خارج الترتيب أو إعادة إرسال متأخّرة قد تمرّ.

**الآن**: ring buffer بآخر **16** طابعاً زمنيّاً (`CMD_WINDOW_SIZE`):
- `isDuplicateCmd`: يفحص النافذة كاملةً → يكتشف التكرار **غير المتتالي**
- `rememberCmd`: دائري (`% CMD_WINDOW_SIZE`) — لا تخصيص ديناميكي (آمن لـESP32)
- مُتحقَّق بالمحاكاة: يكتشف t1 بعد t2/t3، ويُخرج t1 بعد 16 أمراً جديداً ✓

هذا أقرب لما وصفته المراجعة (replay window) من المعرّف الواحد.

## ٢. watchdog (تعافٍ تلقائي)
**المشكلة**: جهاز ESP32 ريفي غير مراقَب قد يتعلّق (شبكة/ذاكرة) ويبقى معطّلاً.
**الحلّ**: `esp_task_wdt` بمهلة 30s:
- `esp_task_wdt_init(30, true)` في setup → panic+reboot عند التعليق
- `esp_task_wdt_reset()` في بداية loop → "أنا حيّ"
- لو علّق loop > 30s → إعادة تشغيل تلقائيّة (تعافٍ بلا تدخّل بشري)

## الحدود الصادقة (لم أبالغ)
- النافذة في الذاكرة (تُفقَد عند إعادة التشغيل) — لتكرار عبر إعادة التشغيل،
  يلزم persisted dedup (NVS flash). تحسين مستقبلي.
- `ts` من `millis()` (وقت التشغيل لا الساعة الحقيقيّة) — clock skew handling
  (NTP) لم يُضَف. المراجعة ذكرته كتحسين — تركتُه (يحتاج NTP + اختبار حيّ).
- النافذة 16 — كافية لتكرار MQTT النموذجي؛ لانقطاع طويل بأوامر كثيرة، أوسع أفضل.

ESP32 + Arduino IDE + المكتبات: painlessMesh/PubSubClient/esp_task_wdt). قد
تظهر مشاكل تجميع (نسخ مكتبات). اختبرها على جهاز فعلي:
- جمّع في Arduino IDE (تأكّد من توفّر esp_task_wdt في ESP32 core)
- اختبار تكرار: `mosquitto_pub` نفس الأمر مرّتين → الصمّام يتحرّك مرّة واحدة
- اختبار watchdog: عطّل loop يدويّاً → اللوحة تعيد التشغيل خلال 30s
