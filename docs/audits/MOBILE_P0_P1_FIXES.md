# إصلاحات الموبايل P0 + P1 — تحت الفشل والتزامن

عالجتُ أعلى أولويّتين من المراجعة: سباق 401 (P0) و idempotency الطابور (P1).

## P0: سباق 401 المتزامن (مُصلَح)
**المشكلة**: عند 401 من عدّة طلبات معاً، الـflag `_isRefreshing` يسمح للأوّل
فقط بالتحديث؛ الباقي يفشل. وخطر deadlock لو لم يُحرَّر القفل.

**الحلّ** (Completer coalescing):
- `_coalescedRefresh()`: كلّ الطلبات المتزامنة تتشارك Completer واحداً →
  تحديث واحد فقط، والكلّ ينتظر نتيجته.
- `whenComplete` يحرّر القفل **دائماً** (لا deadlock حتّى عند الفشل).
- `is_refresh: true` على طلب التحديث → يتخطّى معالج 401 (لا حلقة تحديث ذاتيّة).
- أُزيل `_isRefreshing` القديم.

**التحقّق** (محاكاة المنطق): 5 طلبات متزامنة → تحديث واحد، القفل يُحرَّر،
التحديث اللاحق منفصل. ✓

## P1: idempotency للطابور offline (مُصلَح)
**المشكلة** (السيناريو الزراعي الحرج): المستخدم يضغط "تشغيل الري" → الشبكة
تنقطع → الطابور يعيد الإرسال عند reconnect → **الـactuator ينفّذ مرّتين**.

**الحلّ**:
- كلّ عمليّة مُغيِّرة (command) تحمل `operation_id` ثابتاً يُولَّد مرّة واحدة عند
  الإنشاء → يبقى نفسه عبر إعادات الإرسال → الخلفيّة تكتشف التكرار وتتجاهله.
- ping/pong/subscribe مستثناة (ليست عمليّات مُغيِّرة).
- الطابور الممتلئ يُسجّل تحذيراً (كان يُسقط بصمت).

**ملاحظة**: هذا يكمّل idempotency الخلفيّة الموجود (`command_store` بـ
`ON CONFLICT command_id DO NOTHING`) — الآن العميل يرسل معرّفاً ثابتاً ليطابقه.
